How Minecraft Whitelist Management Works in Agrelha

Long image

A

Answer

Agrelha manages access through a non-destructive RCON probe, dual-write GitOps persistence, and environment-based UUID pre-resolution.

  1. Probing uses a temporary /whitelist on probe to infer status because modern Minecraft dropped /whitelist status.1
  2. Add and remove actions apply instantly via RCON and save to GitOps for restart persistence.1
  3. The container resolves player names to UUIDs at boot using the WHITELIST environment variable.2
  4. Every access change emits an immutable audit record with actor identity and target player.1

How does Agrelha probe whitelist status without modifying state?

Diagram structure
  • Agrelha Engine agrelha
  • Minecraft Server rcon
  • agrelha → rcon · /whitelist on
  • rcon → agrelha · Whitelist is already turned on
  • agrelha → rcon · /whitelist on (if was off)
  • rcon → agrelha · Whitelist is now turned on
  • agrelha → rcon · /whitelist off (immediate rollback)

Modern Minecraft removed /whitelist status. Agrelha issues /whitelist on and checks the response text. If the server answers with already, the whitelist was already active. If it answers with now, Agrelha immediately sends /whitelist off to restore disabled state.

  1. Probe Command ↗

    Agrelha transmits /whitelist on across RCON.

  2. Branch Check ↗

    The parser inspects the response for already or now.

  3. State Revert ↗

    If now appeared, Agrelha sends /whitelist off instantly.

How are player access modifications kept in sync?

Diagram structure
  • Operator UI admin
  • Agrelha Core control
  • GitOps Store git
  • Minecraft Server mc
  • admin → control · Add player request
  • control → git · Patch whitelist.txt commit
  • control → mc · /whitelist add player
  • control → mc · /whitelist reload
  • mc → control · Reloaded whitelist

Live server state and declarative GitOps configurations stay aligned through dual writes. A single API call modifies the in-memory game state and commits to whitelist.txt.

  1. GitOps Patch ↗

    Agrelha writes the username into whitelist.txt in Git.

  2. Live RCON Add ↗

    Agrelha issues /whitelist add to admit the player immediately.

  3. Live Reload ↗

    Agrelha reloads server memory so changes take effect without restart.

Why does container startup require WHITELIST rather than WHITELIST_FILE?

The container entrypoint mc-image-helper handles usernames differently based on configuration format. Passing usernames via environment variable triggers PlayerDB and Mojang UUID lookups before server launch.

ApproachStartup UUID ResolutionOffline / Modded SafetyGitOps Compatibility
WHITELIST env varOnline UUIDAutomatic lookupPre-cachedHigh resilienceConfigMap key mapping
WHITELIST_FILE mountRaw namesSkips image helperUnresolvedRisk of join errorsDirect file volume

UUID resolution requirement

Passing declarative values through WHITELIST lets mc-image-helper query Mojang APIs before server startup. Mounting files directly leaves raw strings without UUID mappings in whitelist.json.
